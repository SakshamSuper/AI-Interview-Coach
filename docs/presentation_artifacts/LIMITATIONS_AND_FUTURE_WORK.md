# AI Interview Coach — Known Limitations & Future Roadmap

Engineering integrity requires transparently documenting known system limitations discovered during development and rigorous testing.

---

## 1. Primary Discovered Limitation: Offline Mock Question Differentiation

### Description
During the 20-company end-to-end simulation audit (evaluating 60 question turns across 20 synthetic company JDs), the platform produced **only 3 unique questions**, resulting in **57 duplicate/near-duplicate question turns** and **0 out of 20 genuinely role-specific interviews**.

### Root Cause Analysis
- The offline `LocalMockLLMClient` (`llm/model.py`) evaluates prompt keywords using simple substring matches:
  `if "python" in prompt_lower: topic = "Python & OOP" ... return GIL question`
- Because the candidate's parsed resume contained `"Python"`, the prompt injected by `QuestionAgent` into `prompt_lower` *always* contained the substring `"python"`.
- Consequently, whether the target role was **NVIDIA Machine Learning Engineer** (requiring PyTorch and CUDA), **Deloitte Data Scientist** (requiring Statistics and R), or **Google Core Systems Engineer** (requiring C++ and Distributed Systems), the mock question generator emitted the exact same CPython GIL concurrency question.

### Remediation Roadmap
1. **Live LLM Provider Integration**: When an active `GROQ_API_KEY` or `OPENAI_API_KEY` is provided, questions are dynamically generated by Llama 3.3 or GPT-4o grounded in target role requirements rather than static fallback heuristics.
2. **Role-Domain Mock Question Bank**: Refactor `LocalMockLLMClient` to prioritize `target_role` and `focus_topics` over resume skills, mapping roles to dedicated question banks across 15 sub-domains (ML, Data Science, Cloud/DevOps, Security, Distributed Systems).

## 2. Secondary Identified Limitations

### 2.1 Synthetic Training Data for ML Readiness Classifier
- **Limitation**: The Scikit-Learn readiness classifier (`ml/predictor.py`) was trained and evaluated on 1,200 synthetic feature vectors generated to simulate interview distributions.
- **Impact**: The model demonstrates high internal statistical consistency (Macro F1 = 0.88), but its predictions do not represent empirically validated real-world hiring outcomes.
- **Remediation**: Collect anonymized, real-world candidate mock interview datasets with ground-truth hiring outcomes.

### 2.2 Local Vector Database Scalability
- **Limitation**: `FAISSVectorStore` currently operates in-memory using local file persistence (`rag/vector_store/index.faiss`).
- **Impact**: Suitable for single-instance deployments and development; does not support distributed vector scaling or live incremental clustering across multiple nodes.
- **Remediation**: Migrate to managed cloud vector databases (Qdrant, Pinecone, or Milvus) for distributed enterprise deployment.

### 2.3 Absence of Interactive Code Execution Sandbox
- **Limitation**: The interview flow evaluates conceptual architecture, algorithmic reasoning, and verbal explanations, but does not provide a live in-browser compiler/sandbox (e.g. Monaco editor + Judge0).
- **Impact**: Candidate coding syntax is evaluated via text input rather than live automated unit test execution.
- **Remediation**: Embed a WebAssembly-based code editor running Pyodide for live Python test-driven execution.

### 2.4 Computer Vision & Eye-Tracking Exclusion
- **Limitation**: Video/computer vision posture and eye-contact monitoring was intentionally deferred to maintain high focus on NLP, LangGraph orchestration, and audio transcription reliability.
- **Remediation**: Optional client-side WebAssembly MediaPipe gaze-estimation module in Phase 2.
